# Building and viewing the docs

The Breeze documentation is one [VitePress](https://vitepress.dev) site: hand-written
guides plus an API reference that [TypeDoc](https://typedoc.org) generates from the
TypeScript source. Both live in `docs/` and share one navigation and one search box.

Nothing is published yet. For now you view the site locally.

---

## TL;DR

```bash
npm install          # once
npm run docs:dev     # then open http://localhost:5173/ and click "API"
```

---

## The commands

| command | what it does | where to look |
|---|---|---|
| `npm run docs:dev` | generates the API reference, then serves the site with hot reload | http://localhost:5173/ |
| `npm run docs:build` | generates the API reference, then builds the static site | `docs/.vitepress/dist/` |
| `npm run docs:preview` | serves the last `docs:build` output, exactly as it would be published | http://localhost:4173/ |
| `npm run docs:api` | regenerates only the API reference markdown | `docs/api/` |

The API reference is at `/api/` on either server — for example
http://localhost:5173/api/classes/EntityManager. VitePress prints the actual URL when it
starts; if the port is taken it picks the next free one.

`docs:dev` and `docs:build` always run TypeDoc first, so the reference matches the source
you have checked out. `docs:dev` then picks up edits to the **guide pages** as you save
them. Edits to **doc comments in `src/`** do not show up until you run `npm run docs:api`
again (or restart `docs:dev`).

`docs:preview` does not rebuild. Run `docs:build` first, or you are looking at an old
build.

Before you commit, run `npm run docs:build`: it is the check that the site still builds,
with no dead links (see [Checks](#checks)).

## How it fits together

```
docs/
  .vitepress/config.mts     site config: nav, sidebars, search
  index.md                  home page
  guide/  query/  metadata/  server/     hand-written pages
  api/                      GENERATED by TypeDoc - do not edit, not committed
typedoc.config.mjs          what TypeDoc documents, and how
src/breeze.ts               the entry point: the API reference is what this exports
```

- **The API reference** is whatever `src/breeze.ts` exports, rendered from the doc comments
  in `src/`. TypeDoc writes markdown into `docs/api/`, plus `docs/api/typedoc-sidebar.json`,
  which `config.mts` imports as the API sidebar. That is why the site cannot start until
  TypeDoc has run once.
- **The guides** are plain markdown under `docs/guide`, `docs/query`, `docs/metadata` and
  `docs/server`. Their sidebars are listed by hand in `docs/.vitepress/config.mts`.
- Generated output — `docs/api/`, `docs/.vitepress/dist/` and `docs/.vitepress/cache/` —
  is gitignored.

## Writing doc comments

The API pages are only as good as the comments in `src/`. TypeDoc reads standard TSDoc
tags (`@param`, `@returns`, `@example`, `@deprecated`, `@see`, `@throws`,
`@defaultValue`) and these Breeze ones, declared in `typedoc.config.mjs`:

| tag | meaning |
|---|---|
| `@adapter` | names the adapter interface a class implements |
| `@eventArgs` | documents the argument type of a `BreezeEvent` |
| `@chainable` | the method returns `this`, so calls can be chained |
| `@summary`, `@event`, `@property` | as in TSDoc |

Two rules that have bitten before:

- **`@param` names must match the real parameter names.** A rest parameter
  (`...args`) is documented as `args`. TypeDoc warns about every mismatch.
- **`@hidden` and `@internal` are not the same thing.**
  - `@hidden` only keeps a declaration out of the docs.
  - `@internal` also removes it from the published `.d.ts`, because the build uses
    `stripInternal`. Never put `@internal` on anything `src/breeze.ts` exports, or on
    anything an exported signature needs: the package's type declarations then refer to
    something that is not there, and fail to compile for users. Use `@hidden` for those.

Types that public signatures mention but that are deliberately not exported are listed in
`intentionallyNotExported` in `typedoc.config.mjs`. Adding a name there, or exporting it
from `breeze.ts` instead, is an API decision — not just a way to quieten a warning.

## Writing guide pages

To add a page, create the markdown file under the right folder and add it to that
section's `sidebar` in `docs/.vitepress/config.mts`. Link to other pages by site path, with
no `.md`: `/guide/saving-changes`, `/query/predicates`, and to the API as
`/api/classes/EntityManager`.

VitePress specifics:

- **Never write `{{` outside a fenced code block.** VitePress pages are Vue templates, so
  `{{ ... }}` in prose — or in inline code — is treated as an expression, and the build
  breaks. Inside fenced code blocks it is fine.
- **A link to a page that does not exist fails the build** (`ignoreDeadLinks: false`). A link
  to an `#anchor` that does not exist does **not** — VitePress does not check those, which is
  what `npm run docs:check-anchors` is for. It runs as the last step of `docs:build`.
- Callouts use `::: tip`, `::: warning` and `::: danger` blocks. Anything a 2.x user would trip
  over belongs in [Migrating from 2.x](docs/guide/migrating-from-2x.md) and UPGRADE.md, not in a
  callout on the page: the `::: tip Changed in 3.0` blocks that used to be scattered through the
  guides were consolidated there.

## Checks

`npm run docs:build` must exit cleanly. It fails on:

- a link to a page that does not exist,
- a link to an `#anchor` that does not exist (`scripts/check-doc-anchors.mjs`, which checks
  every link against the ids the built HTML actually emitted), or
- a `{{` that Vue could not compile.

TypeDoc should also report **0 warnings**. It prints them during `docs:api`, `docs:dev`
and `docs:build`; the usual causes are a stale `@param` name, an unknown tag, a public
signature that mentions a type which is neither exported nor listed in
`intentionallyNotExported`, or a newly exported symbol that
`scripts/typedoc-categories.mjs` has no category for.

TypeDoc reads **one** entry point, `scripts/docs-entry.ts`, which re-exports `src/breeze.ts`
plus the two optional mixins. Its header says why that rather than three entry points; the
short version is that several entry points would move every page under `/api/breeze/` and
would stop the category plugin working. A new public symbol appears in the reference by
itself, and the plugin warns until it has been placed in a category.

Note that TypeScript, and so TypeDoc, reads only the **last** doc comment before a declaration.
Two stacked `/** ... */` blocks mean the first one's tags are silently discarded — `@hidden
@internal`, which decides whether a member reaches the published `.d.ts` and the reference, and
`@deprecated`, which decides whether an editor warns anybody. It reads as two comments about the
same thing and has happened five times here, so `side-effects.spec.ts` now fails on it.

## Troubleshooting

**The site fails to start with an error about `typedoc-sidebar.json`**
You ran `vitepress dev docs` (or `build`) directly, before TypeDoc had generated the API
reference. Use the `npm run docs:*` scripts, or run `npm run docs:api` once first.

**My doc-comment change does not show up**
`docs:dev` generates the API reference only when it starts. Run `npm run docs:api` in a
second terminal, or restart `docs:dev`.

**The build fails on a dead link after renaming a page**
Fix every link to the old path, and the page's entry in `docs/.vitepress/config.mts`.

**An API page is missing a class or function**
The reference documents only what `src/breeze.ts` exports. Check it is exported there, and
that its declaration is not tagged `@hidden` or `@internal`.

**Port 5173 (or 4173) is already in use**
VitePress moves to the next free port and prints it. Use the URL it prints.
